# C4

A system seen in layers: who uses it, which parts it splits into and which other systems it depends on. It follows Simon Brown's C4 model. One JSON model describes the software once; each view is drawn from it by `scripts/build_c4.py`, with layout by elkjs and the poster gate (`build.py` and `poster_lint.py`).

Template: `templates/11-c4/`, in the skill folder: `_src/11-c4-pix.json` and the three views it draws, one per C4 level: context, containers and the components of the API.

## When to use

- "C4", "context diagram", "container diagram", "component diagram", "system view", "system landscape";
- presenting a system to someone who does not know it: what is inside, what is outside and how each part talks;
- documenting dependencies between systems of different teams;
- the order of the calls of one feature across containers (dynamic view), or where each container runs (deployment view);
- the request comes with a Structurizr `workspace.dsl`: import it (below).

If the subject is AWS infrastructure in detail (network, subnets, security groups), it is an architecture poster. If it is the exact order of calls and replies inside one operation, with waiting, `alt` or `loop`, it is a sequence diagram. The C4 dynamic view stays at the level of who calls whom, in order.

## The model

Write only the model; position and routing are computed. Keys are in English.

```json
{
  "lang": "pt-BR",
  "header": ["ai-diagrams · Sistema de cobrança", "C4 · V1"],
  "footer": ["ai-diagrams · modelo C4", "cobrança"],
  "main": "containers",
  "elements": [
    {"id": "cliente", "type": "person", "name": "Cliente PJ", "description": "emite boletos"},
    {"id": "cobranca", "type": "system", "name": "Sistema de cobrança", "description": "emite e baixa boletos"},
    {"id": "cip", "type": "system", "external": true, "owner": "CIP", "name": "Nova Plataforma de Cobrança", "description": "registro do boleto"},
    {"id": "api", "type": "container", "parent": "cobranca", "technology": "Node.js em Lambda", "icon": "aws://compute/lambda.png", "name": "API de cobrança", "description": "valida e grava o boleto"},
    {"id": "banco", "type": "container", "parent": "cobranca", "shape": "database", "technology": "DynamoDB", "name": "Banco de cobrança", "description": "boletos e eventos"},
    {"id": "rotas", "type": "component", "parent": "api", "technology": "Fastify", "name": "Rotas de boleto", "description": "recebe a emissão"}
  ],
  "relationships": [
    {"from": "cliente", "to": "rotas", "description": "Emite boletos", "technology": "HTTPS · JSON"},
    {"from": "rotas", "to": "cip", "description": "Registra o boleto", "technology": "HTTPS · certificado"}
  ],
  "views": [
    {"type": "context", "key": "context", "scope": "cobranca", "title": "...", "description": "..."},
    {"type": "container", "key": "containers", "scope": "cobranca", "title": "...", "description": "..."}
  ]
}
```

### Elements

| `type` | Inside (`parent`) | Required | Drawn as |
|---|---|---|---|
| `person` | nothing | name, description | dark box with a head |
| `system` | nothing | name, description; `external: true` for a system of another company, `owner` for who runs it | box; in the accent tint when in focus, blue when it is another system of the company, dashed and gray when external |
| `container` | a `system` | name, description, technology | box; `shape` changes it |
| `component` | a `container` | name, description, technology | box with the two tabs of the UML component |
| `deploymentNode` | nothing (with `environment`) or another `deploymentNode` | name; technology and `instances` optional | frame around what runs in it |
| `infrastructureNode` | a `deploymentNode` | name, technology | light gray box (gateway, queue, bucket, DNS) |
| `containerInstance` | a `deploymentNode` | `container`: the id of the container | the container's box |

`shape`: `web` (browser bar), `database` (cylinder), `queue` (pipe), `mobile` (device). `icon`: an `aws://category/file.png` icon in the corner, only when the platform is AWS.

Text: description in lowercase, one short sentence of what the element is or does. The type word, the technology and the owner go in the first line of the box, written by the generator in the diagram's language.

### Relationships

- Each relationship has `from`, `to`, `description` (what it does, starting with a verb) and `technology` (`HTTPS · JSON`, `SQL`, `gRPC`, `SFTP → S3 → SQS`).
- Write each relationship once, at the most detailed level known: `cliente → rotas` (a component). The container view draws it as `cliente → API de cobrança`, and the context view as `cliente → Sistema de cobrança`. When the same pair appears more than once at a level, the first one is drawn.
- A relationship written at the level of the view wins over an implied one: `cliente → cobranca` with its own description is what the context view shows.
- The arrow leaves the caller and points to the callee. A reply does not get its own arrow, except in a dynamic view.
- Between deployment elements (`infrastructureNode`, `containerInstance`), write the relationship with their ids. Relationships between containers become relationships between their instances in the deployment view.

### Views

| `type` | `scope` | Shows |
|---|---|---|
| `landscape` | none | every person and system |
| `context` | a system | the system as one box, the people and systems related to it |
| `container` | a system | the system as a boundary with its containers; outside, the people and systems related to them |
| `component` | a container | the container as a boundary with its components; outside, the other containers, people and systems related to them |
| `dynamic` | a system, a container or none | `steps`: `[{from, to, description, technology}]`, numbered in order; elements of any level. A step without technology takes it from the relationship between the same pair |
| `deployment` | a system | the deployment nodes of `environment` that hold an instance of a container of the system, nested as frames |

Each view has a unique `key` (lowercase, digits and hyphens) and may have `title`, `description` (the subtitle), `label` (its name in the navigation), `kicker`, `include` and `exclude` (lists of element ids that narrow what it shows) and `orientation`.

`orientation` sets the direction of the layout: `auto` (default) tries left to right and top to bottom and prefers the drawing whose page is landscape; `horizontal` lays out left to right only and accepts a page up to 2560 px wide (slide, book spread); `vertical` lays out top to bottom only, the 0.2.0 behavior. Set it on the model to change the default for every view; a view's own `orientation` wins.

`main` names the view written as `<name>.html`; the others are `<name>-<key>.html`. Without `main`, it is the container view.

## What the generator draws

- Color says the role: the system in focus, its containers and its components in the accent tint (`c4_focus`, border `c4_focus_border`); another system of the company in blue (`c4_internal`, `c4_internal_border`); an external system dashed and gray (`c4_external`); a person dark. The colors come from `derived` in the theme; a theme without these four keys keeps the gray boxes of 0.2.0.
- Each arrow carries its own label: the description and `[technology]`, on the arrow, which runs behind the label. When no stretch of the arrow is long enough, the label goes beside it, aligned to the arrow. A label never touches a box, a frame border, another arrow or another label; when there is no room, the layout opens more space and tries again. It stops with `C4-NO-ROOM` only when no layout fits.
- elkjs places and routes; several variants are tried (model order, node placement, people and callers on top, systems that are only called at the bottom, more spacing) and the one with the fewest crossings, then the fewest bends, the shortest arrows and the smallest area wins. In a dynamic view, a reply is laid out parallel to the call it answers.
- Boxes of the same kind with similar heights get the same height; the heights and label sizes are measured in Chrome with the default theme, so the geometry does not change with the theme.
- The boundary name goes in the first stretch of its border that no arrow crosses.
- The legend lists only what the view draws. The navigation under the subtitle links every view of the model; a system or container that has a deeper view gets an "open" link to it, and the whole box opens it.
- A dynamic view also lists its steps under "Sequence", with the full sentence.

## Commands

```bash
python3 <skill>/scripts/build_c4.py diagrams/_src/NN-name.json
```

It writes one source per view next to the JSON and builds each one through `build.py`. `--no-build` writes only the sources. `--lang` and `--theme` work as in the other generators.

Structurizr DSL:

```bash
npx ai-diagrams import workspace.dsl --out diagrams/name --lang pt-BR
```

The importer reads people, software systems, containers, components, relationships (also `-> b` and `this -> b` inside a block), groups, enterprise, deployment environments with deployment nodes, infrastructure nodes and container instances, the landscape, context, container, component, dynamic, deployment and filtered views (`include *`, identifiers, `exclude`, `title`, `description`, `autoLayout`: `lr`/`rl` becomes `orientation: horizontal`, `tb`/`bt` becomes `vertical`, bare `autoLayout` leaves `auto`), and the shapes in `styles`. Colors in `styles` and `theme` are ignored: the colors are the theme's. Anything else stops with `DSL-UNSUPPORTED: <keyword> at line N`. A system is external with the tag `External`, `location External`, or when it is outside the `enterprise` block. The DSL keeps the model's rules: a container or relationship without technology fails with `C4-NO-TECHNOLOGY`; add the technology after the description.

## Gate

Before drawing, the generator stops with `C4-DUPLICATE`, `C4-UNKNOWN`, `C4-PARENT`, `C4-NO-DESCRIPTION`, `C4-NO-TECHNOLOGY`, `C4-SHAPE`, `C4-VIEW` or `C4-NO-ROOM` (the docstring of `build_c4.py` says when).

Then the poster gate, with these C4 rules:

- `C4-NO-TYPE`: a `.bchip.c4` element without `.bn` or without `.bt`;
- `C4-NO-LEGEND`: a page with a C4 element and without `.c4leg`;
- `C4-REL-MISSING`: a page with `.rel` labels where an arrow has no label, or a label has no arrow; such a page does not need badges or `.passos`;
- `C4-REL-INCOMPLETE`: a label without the description or the `[technology]`;
- `C4-REL-DETACHED`, measured in Chrome: a label more than 14px from its own arrow;
- `OVERLAP` and `ARROW-OVER-TEXT` also cover the labels: no label over a box, a frame name or another label, and no other arrow across a label.

## When reading the PNG

- who is inside and who is outside the boundary is visible without reading the labels;
- every person and every external system has at least one relationship;
- each label reads as part of its own arrow;
- no long detour: if an arrow goes around the drawing, check the model (a relationship in the wrong direction, or a view showing too much; narrow it with `include` or `exclude`).
